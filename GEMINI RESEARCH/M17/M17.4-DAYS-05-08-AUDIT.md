## Day 5 — Client and Server

### Current Curriculum

- **Phase:** 1 — Digital Foundations. **Sub:** `network`.
- **Objectives:** explain the client-server model and where computation happens; distinguish
  frontend, backend, and the API boundary; decide which side a given piece of logic belongs on.
- **Lesson structure:** Concept intro (10m, client asks/server answers, client code is visible to
  the user) → Core material (20m, frontend/backend split, the API as the contract between them,
  why AI provider keys must never live in frontend code) → Hands-on (15m, watch the Network tab
  in dev tools during a real action) → Practice (10m, assign five quiz-feature responsibilities to
  client or server) → Reflection (5m, why client-side score calculation is a design flaw in a
  graded course).
- **Example:** a leaked LLM API key embedded in frontend JavaScript — diagnosed as an
  architecture problem, not a developer mistake.
- **Practice/Challenge:** sketch an AI quiz generator's request flow, mark where the key and data
  live and where an attacker could interfere; describe an end-to-end AI-summary request flow.
- **Recap (Indonesian):** correctly restates client/server, frontend/backend, and the API
  boundary; misconception block correctly targets "minified code is hidden" as false security.
- **Resources (2, both `verified: true`):** MDN "Client-Server overview" (via the general MDN
  Learn hub URL) and MDN Glossary: Server (specific, focused).
- **Quiz (5 questions):** why API keys must stay server-side; frontend does not need the DB
  schema; server-side pass/fail computation; sound AI-summary request flow; short-answer on
  server-vs-client responsibility split.

### Pedagogical Audit

1. **Accuracy** — correct throughout. The client/server, frontend/backend, and API-boundary
   framing match how these concepts are taught in standard web-architecture references.
2. **Clarity** — strong. "A client asks. A server answers." is an effective one-line anchor: no
   unexplained jargon, terms are defined in use.
3. **Depth** — appropriate for Day 5 of 28; doesn't wander into specific frameworks or hosting
   models, which belong later.
4. **Practicality** — high. The Network-tab hands-on task makes an abstract boundary visible in a
   tool every learner already has open daily.
5. **Examples** — the leaked-key example is concrete, realistic, and correctly diagnosed as an
   architecture failure rather than a one-off mistake — this is the single most consequential
   security lesson for anyone about to build with AI APIs, and it lands early and clearly.
6. **Active learning** — yes: live Network-tab observation, a responsibility-sorting exercise, and
   a sketch-the-architecture practice task that is reused conceptually through the rest of the
   curriculum.
7. **Misconceptions** — explicitly addressed: minification is not security.
8. **Current relevance** — no gap identified. The AI-key-security framing is already exactly the
   modern context this day needs; nothing found in research changes or extends it.
9. **Resource quality** — good, with one minor observation: the first resource's stored URL
   (`https://developer.mozilla.org/en-US/docs/Learn`) points at MDN's general web-development
   learning hub, not a page specific to client-server architecture — see Research Findings.
10. **Assessment alignment** — all three objectives are directly tested: q1/q4 test the API-key
    security consequence of the client-server split; q2 tests the frontend/backend boundary; q3
    tests the "decide which side logic belongs on" objective for a consequential decision
    (pass/fail). No gap found.

## Day 6 — Web Fundamentals

### Current Curriculum

- **Phase:** 1. **Sub:** `web`.
- **Objectives:** describe the roles of HTML, CSS, and JavaScript; explain what the browser does
  when it receives a page; inspect and modify a live page using developer tools.
- **Lesson structure:** Concept intro (10m, three separable concerns — structure/presentation/
  behaviour — and the DOM) → Core material (20m, semantic HTML and why it matters for
  accessibility/search/AI scrapers, the CSS cascade, JS manipulating the DOM after load, direct
  relevance to SCORM/xAPI/LMS themes) → Hands-on (15m, live-edit the DOM via Inspect Element,
  observe the edit is local-only) → Practice (10m, hand-write a minimal HTML+CSS page) →
  Reflection (5m, why local DOM edits don't persist for other users).
- **Example:** a course page that visually looks like it has headings but structurally has none —
  correctly diagnosed as an accessibility failure caused by styling text instead of using
  semantic elements.
- **Practice/Challenge:** build a semantic page from scratch with one JS interaction; critique an
  existing LMS page's HTML structure for non-visual reasons.
- **Recap (Indonesian):** accurate; correctly frames the DOM, semantic HTML, and the
  SCORM/xAPI/LMS relevance for this specific learner audience.
- **Resources (2, both `verified: true`):** MDN "Learn web development" (same URL/observation as
  Day 5's first resource — see above) and freeCodeCamp's Responsive Web Design certification.
- **Quiz (6 questions):** why semantic elements matter over styled-to-look-like text; DOM edits
  are local-only; correct HTML/CSS/JS role pairing; diagnosing a failed accessibility audit; DOM
  definition; short-answer on CSS's job.

### Pedagogical Audit

1. **Accuracy** — correct throughout. The structure/presentation/behaviour separation, DOM
   description, and semantic-HTML-drives-accessibility claim are all standard and correctly
   stated; the SCORM/xAPI/LMS-theme framing is accurate for this project's specific audience.
2. **Clarity** — strong; the "three separable concerns" framing is a clean mental model, reused
   consistently through the segment.
3. **Depth** — appropriate; doesn't reach into build tooling, frameworks, or the CSSOM, which
   would be premature at Day 6.
4. **Practicality** — high. Live-editing the DOM and observing it doesn't persist is a genuinely
   memorable, hands-on demonstration of a concept (client-only state) that recurs all through the
   curriculum.
5. **Examples** — the "looks like a heading, isn't one" example is concrete and directly testable
   by the learner on any real page; it correctly separates the visual and structural claims.
6. **Active learning** — yes: live DOM editing, hand-writing a page from scratch, and a
   real-LMS-page critique task that connects directly to the learner's stated career context.
7. **Misconceptions** — explicitly addressed: choosing an element for its default size rather
   than its meaning.
8. **Current relevance** — no gap identified. The "AI scrapers rely on semantic meaning" line
   already anticipates the current relevance question research would otherwise raise.
9. **Resource quality** — same observation as Day 5: the first resource is the general MDN
   web-development hub rather than a Day-6-specific page, though (unlike Day 5) this day's own
   topic — HTML/CSS/JS fundamentals — is closer to that hub's actual primary subject matter, so
   the breadth concern is less material here.
10. **Assessment alignment** — objectives 1 (roles of HTML/CSS/JS) and 2 (what the browser does
    with a page) are directly tested (q1, q3, q4, q5, q6). Objective 3 ("inspect and modify a live
    page using developer tools") is a hands-on skill objective; q2 tests understanding of *why*
    such edits don't persist, which is the conceptual half of that objective — the physical skill
    itself is naturally not testable by a written quiz, consistent with how every other day in

## Day 7 — APIs

### Current Curriculum

- **Phase:** 1. **Sub:** `api`.
- **Objectives:** read API documentation and identify endpoint/method/auth/request/response; make
  a real API call and interpret the result; explain why AI model providers expose their models as
  APIs.
- **Lesson structure:** Concept intro (10m, API as a documented contract, every AI capability the
  learner will build on is reached this way) → Core material (20m, the five things that define a
  REST-style call, auth/rate-limits/cost, how to read documentation top-down) → Hands-on (15m,
  call a public unauthenticated API and match the JSON response fields to their documented
  meaning) → Practice (10m, write out the full shape of a hypothetical LLM API request without
  sending it) → Reflection (5m, why an API beats direct database access as an integration point).
- **Example:** an LMS migration where API-based reports survived unchanged while database-coupled
  reports all broke — correctly frames the API as a stable contract versus an implementation
  detail.
- **Practice/Challenge:** document one real AI-provider endpoint's shape; name four production-
  readiness checks beyond "does the call succeed once."
- **Recap (Indonesian):** accurate; the "API is not a database — you can only call what's
  offered" framing is a clean, correctly-targeted misconception fix.
- **Resources (2, both `verified: true`):** MDN "HTTP request methods and headers" and Postman
  Learning Center (both specific, focused, non-redundant with each other).
- **Quiz (6 questions):** the five elements of a REST call; GET vs. POST; API vs. direct DB access
  as an integration point; HTTP-success-but-app-level-failure diagnosis; where an API key belongs
  in a request; short-answer on the five questions to answer from documentation before coding.

### Pedagogical Audit

1. **Accuracy** — correct throughout, including the specific and correct claim that a 200 status
   with an error payload is a real, distinct failure mode from a transport-level failure.
2. **Clarity** — strong; "five things define any REST-style API call" is a concrete, checkable
   list rather than a vague description.
3. **Depth** — appropriate; deliberately deferred to Days 20/22 for tool-calling-specific and
   security-specific API concerns, which is the correct place for them.
4. **Practicality** — high; calling a real public API and matching fields to documentation is
   exactly the skill the learner will need for every AI-provider integration later in the
   curriculum.
5. **Examples** — the migration example is realistic and precisely targets the stated objective
   (API as stable contract vs. schema as implementation detail).
6. **Active learning** — yes: a real API call, a documentation-reading exercise, and a
   write-the-request-shape practice task that rehearses the exact skill needed before Phase 4.
7. **Misconceptions** — explicitly addressed ("API is not a database").
8. **Current relevance** — no gap identified for the stated objectives (documentation literacy,
   REST mechanics, and the rationale for API-based model access). Streaming responses and
   OAuth-style token exchange were considered as possible additions and judged premature: this
   day's objectives are about REST literacy in general, and both topics are more naturally placed
   nearer Phase 4 (Days 16–20) where the curriculum starts working with a specific LLM API
   directly — adding them here would be teaching ahead of where the learner can use them, which
   is exactly the "interesting but not needed here" trap the audit instructions warn against.
9. **Resource quality** — good. Both resources are specific, non-redundant, and appropriately
   sourced (MDN for HTTP mechanics, Postman for the practical testing tool); the Postman URL was
   already back-verified to its canonical path in an earlier session (M9/M10) and re-confirmed
   reachable and on-topic this session (see Research Findings).
10. **Assessment alignment** — objectives 1 and 2 (reading docs, making a call, interpreting the
    result) are well covered by q1, q4, q5, and q6. **Objective 3 — "explain why AI model
    providers expose their models as APIs" — has no dedicated question.** The existing six
    questions test general REST mechanics competently but none specifically probes the reasoning
    behind API-based model delivery (e.g., centralised compute, no local weights to manage,
    metered access, provider-side model updates without client changes). This is a genuine,
    non-manufactured gap between what is taught (the concept intro states it directly: "Every AI
    capability you will build on... is reached this way") and what is assessed.

### Research Findings

Opened directly: `https://developer.mozilla.org/en-US/docs/Web/HTTP`, the exact stored URL for
this day's first resource. **FACT** (confirmed by opening the page): it resolves directly with no
redirect, current title "HTTP: Hypertext Transfer Protocol | MDN", and comprehensively covers
request methods, the full current header set (170+, including security headers such as CORS/CSP),
authentication, and the complete status-code reference (1xx–5xx) — the resource fully supports
what the lesson claims it supports, with no currency concerns found.

### Enhancement Opportunities

The pedagogical audit surfaced one genuine gap: **the assessment does not test objective 3** (why
AI providers expose models as APIs), even though the lesson's own concept-introduction paragraph
states the reasoning. This is an assessment-alignment finding, not a content or resource finding —
per the task's explicit instruction, it is flagged as an issue for future revision, not
implemented or rewritten this session.

### Decision

**VERIFY BEFORE CHANGE** — specifically for the assessment-alignment question only. The lesson
content itself is **KEEP** (accurate, clear, appropriately scoped, resources current); only the
post-test's coverage of objective 3 is flagged, and per the task's explicit instruction ("If
something needs attention, document the issue rather than silently rewriting it"), no question
was added or modified.

### Priority

**P3** — the gap is real but low-stakes: objective 3 is a "why" (rationale) objective rather than
a skill objective, the concept is stated clearly in the lesson, and five of six existing questions
already test the two skill-based objectives well. This is a future-revision candidate, not an
urgent fix.

### Evidence

Direct inspection of the current quiz array (6 questions, all read and cross-checked against the
3 stated objectives) — no external source needed to establish this finding; it is a structural
observation about the existing content, not a claim about the outside world.

### Implementation Notes (not applied this session)

Per instruction, no question was written or proposed. If addressed in a future session, the
natural fit would be a seventh question or a replacement for one of the existing REST-mechanics
questions (there is some redundancy between q1's "five elements" question and the sa question's
"five questions to answer from docs" — both test document-reading structure, which is one place a
future question on "why APIs" could be substituted rather than purely added, keeping the quiz at
six items).

### Estimated Time Impact

None (no lesson content change).

### Assessment Impact

**ASSESSMENT ISSUE — FUTURE REVISION.** Objective 3 ("explain why AI model providers expose their
models as APIs") is taught but not directly assessed. See Enhancement Opportunities and
Implementation Notes above. Not acted on this session.

### Resource Impact

None. Both resources confirmed current, specific, and non-redundant.

## Day 8 — Databases

### Current Curriculum

- **Phase:** 1. **Sub:** `database`.
- **Objectives:** explain tables/rows/columns/keys/relationships; distinguish relational from
  document and vector databases by the problem each solves; write a simple query in plain language
  and translate it to SQL structure.
- **Lesson structure:** Concept intro (10m, database = storage + query engine + guarantees; the
  relational table/key model) → Core material (20m, primary/foreign keys and the classic
  learners/courses/enrolments shape, SQL as declarative "what" not "how", document databases for
  flexible-shape data, vector databases as the RAG storage layer with an explicit forward
  reference to Day 19) → Hands-on (15m, design three LMS tables on paper, write five plain-language
  questions the system must answer) → Practice (10m, translate two of those questions into SQL
  shape) → Reflection (5m, why a comma-separated list in one row eventually causes pain).
- **Example:** an LMS completions field stored as a comma-separated string, breaking any
  aggregate query — correctly diagnosed as a normalisation failure with a concrete fix.
- **Practice/Challenge:** model learners/courses/enrolments/quiz-attempts; argue, before Day 18,
  what kind of database an AI assistant over internal documents needs and what it actually stores.
- **Recap (Indonesian):** accurate; correctly frames the three database types by the question each
  answers rather than by which is "more modern."
- **Resources (2, both `verified: true`):** PostgreSQL's official tutorial and freeCodeCamp's
  SQL/databases learning path.
- **Quiz (6 questions):** foreign-key role; bad relational design (comma-separated list); which
  database type answers a semantic-similarity question; relational databases for transactional
  accuracy; which SQL clause filters rows; short-answer on why structure determines which
  questions are cheap to answer later.

### Pedagogical Audit

1. **Accuracy** — correct throughout, including the specific and important claim that SQL is
   declarative ("what", not "how") and that the query planner — not the author — decides
   execution strategy.
2. **Clarity** — strong; "storage plus a query engine plus guarantees" is a compact, accurate
   definition that immediately motivates why ad hoc files/spreadsheets fail at scale.
3. **Depth** — appropriate; correctly stops short of normalisation forms, transaction isolation
   levels, or index internals, all of which would be premature here.
4. **Practicality** — high; designing real LMS tables on paper and translating real questions into
   SQL shape is the actual skill, not a toy exercise.
5. **Examples** — the comma-separated-completions example is realistic (this is a genuinely common
   beginner mistake) and precisely demonstrates the stated reflection question.
6. **Active learning** — yes: table design, plain-language question writing, and SQL-shape
   translation form a coherent three-step exercise building toward the same artifact.
7. **Misconceptions** — explicitly addressed: database choice is about which question needs to be
   fast, not about recency/fashion.
8. **Current relevance** — no gap identified. The vector-database forward reference to Day 19 is
   already the modern-context element this day needs, and it is placed correctly (introduced, not
   taught in depth, with an explicit signpost to where the depth arrives).
9. **Resource quality** — good; PostgreSQL's own tutorial is a strong primary source, and
   freeCodeCamp's path is practice-oriented and complementary rather than redundant.
10. **Assessment alignment** — objective 1 (tables/rows/keys/relationships) is well tested (q1,
    q2, q5). Objective 2 (distinguish relational from document and vector by problem solved) is
    **partially** tested: q3 tests vector databases and q4 tests relational-for-transactions, but
    **no question tests document databases**, the third of the three types the objective names.
    Objective 3 (translate plain language to SQL structure) is tested at the syntax-recognition
    level (q5) rather than the translation-skill level, which is the same hands-on-skill caveat
    seen elsewhere in this curriculum and not classified as a gap on its own.

### Research Findings

No external research opened for Day 8. The pedagogical audit found the lesson content strong and
appropriately scoped; the one finding (document databases untested) is a structural observation
about the existing quiz, not a claim requiring outside verification.

### Enhancement Opportunities

None for lesson content. One assessment-alignment observation: document databases are taught
(one paragraph, correctly scoped) but never assessed, while the other two database types named in
the same objective (relational, vector) each get a dedicated question.

### Decision

**VERIFY BEFORE CHANGE** — for the assessment-alignment question only, same shape as Day 7. Lesson
content itself is **KEEP**.

### Priority

**P3** — minor; document databases are the least-emphasised of the three types in the lesson body
itself (one paragraph, versus more developed treatment of relational and vector), so the
assessment gap is proportionate to the lesson's own emphasis rather than a mismatch with it. Not
urgent.

### Evidence

Direct inspection of the current quiz array (6 questions, cross-checked against the 3 stated
objectives) — a structural observation about existing content, no external source needed.

### Implementation Notes (not applied this session)

Not written or proposed, per instruction. If addressed in a future session, a natural approach

relational-vs-vector only, rather than adding a seventh question.

### Estimated Time Impact

None (no lesson content change).

### Assessment Impact

**ASSESSMENT ISSUE — FUTURE REVISION.** Document databases (named explicitly in objective 2) are
taught but not assessed by any of the 6 quiz questions. Not acted on this session.

### Resource Impact

None. Both resources confirmed appropriate; no external verification was needed to reach that
conclusion (no currency-sensitive or ambiguous claim was at stake).
