## Day 9 — Programming Logic, Variables and Control Flow

### Current Curriculum

- **Phase:** 2 — Programming Foundations. **Sub:** `programming`.
- **Objectives:** explain variable/type/condition/loop without code; trace a short program by
  hand; write and run a small Python script.
- **Lesson structure:** Concept intro (10m, sequence/selection/repetition, variable/type) → Core
  material (20m, Python's core types incl. dict-as-JSON, `==` vs `=`, for vs while and their
  classic failure modes) → Hands-on (15m, write a quiz-score-list script with a pass condition) →
  Practice (10m, extend it to count below-70 scores, deliberately without looking up a solution
  first) → Reflection (5m, what did an error message actually say).
- **Example:** a `TypeError` from adding `int` and `str` — reads the error message as diagnostic
  evidence rather than something to fear.
- **Resources (2, both `verified: true`):** the official Python Tutorial (Python Software
  Foundation), freeCodeCamp Scientific Computing with Python.
- **Quiz (6 questions):** TypeError diagnosis; `==`/`=` distinction; correct loop type for a known
  collection; infinite-loop cause; dict-as-JSON-object mapping; short-answer on why reading the
  full error beats guessing.

### Pedagogical Audit

1. **Accuracy** — correct throughout; the three-construct framing (sequence/selection/repetition)
   and the dict↔JSON shape claim both hold.
2. **Clarity** — strong; no unexplained jargon, terms defined in use.
3. **Depth** — appropriate for the first programming day; does not overreach into functions
   (deferred correctly to Day 10) or exceptions-as-a-formal-topic.
4. **Practicality** — high; the hands-on task is a real, runnable script tied to something the
   learner already understands (quiz scores), not a toy `print("hello")`.
5. **Examples** — the `TypeError` example models the actual diagnostic skill (read the error,
   don't guess) rather than just describing it.
6. **Active learning** — yes: write, extend, and reflect on a real script; explicitly told to hit
   the error first rather than look up a solution.
7. **Misconceptions** — `==` vs `=` addressed directly and accurately (Python's syntax error on
   `if x = 5:` is correctly described as a kindness, not a hazard).
8. **Current relevance** — no gap found. Python's `int`/`float`/`str`/`bool`/`list`/`dict` core
   types and its role as the dominant AI/ML language are unchanged facts, not time-sensitive ones.
9. **Resource quality** — both resources official/appropriately leveled; no redundancy or
   over-advanced material.
10. **Assessment alignment** — all three objectives are tested: q1/q2 test variable/type/condition
    vocabulary and the `==`/`=` distinction; q3/q4 test loop tracing (correct loop choice, infinite
    loop diagnosis); q5 tests the dict/JSON claim from Core material; q6 tests the debugging habit
    the Example modeled. Strong, direct coverage.

## Day 10 — Functions, Data Structures and JSON in Practice

### Current Curriculum

- **Phase:** 2 — Programming Foundations. **Sub:** `programming`.
- **Objectives:** write functions with clear inputs/outputs; choose list vs. dict for a given
  problem; load and navigate JSON in Python.
- **Lesson structure:** Concept intro (10m, function as reusable transformation) → Core material
  (20m, parameters/return values, list-vs-dict tradeoff, `json.loads`/`json.dumps`, navigating
  nested API-response JSON) → Hands-on (15m, write `score_summary(scores)` that returns rather
  than prints) → Practice (10m, count total activities in a nested course/module/activity JSON
  structure) → Reflection (5m, why return beats print).
- **Example:** an LLM API response where the generated text isn't reliably the first content
  block — the robust fix is to filter by block `type`, not position.
- **Resources (2, both `verified: true`):** Python docs on functions/control flow, Python docs on
  the `json` module.
- **Quiz (6 questions):** return-vs-print reasoning; list-vs-dict lookup choice; `loads`/`dumps`
  direction; robust API-response parsing by type not position; parameter-default rationale;
  short-answer on when a list beats a dict.

   `shared/tool-use-concepts.md` in this project's own reference material, though not opened as an
   external source here since the lesson's own claim was already correct on inspection) are
   actually shaped: content arrives as an ordered list of typed blocks, and filtering by `type`
   rather than trusting position is the documented robust pattern.
2. **Clarity** — strong.
3. **Depth** — appropriate; correctly stops at "filter by type," not a full JSON-schema or
   type-hinting digression.
4. **Practicality** — high; the hands-on task (`score_summary`) and the "quiz score analyser v2"

5. **Examples** — the API-response example is not generic filler; it is a real, forward-looking

6. **Active learning** — yes: refactor into `load`/`analyse`/`report`, save output as JSON.
7. **Misconceptions** — print-is-not-return addressed directly and correctly.
8. **Current relevance** — no gap. The `json` module's `loads`/`dumps` API and the type-not-position
   parsing principle are stable, not time-sensitive.
9. **Resource quality** — both official Python docs, correctly scoped (control-flow page for
   functions, json module page for the second half).
10. **Assessment alignment** — all three objectives tested directly: q1/q5 test function design

## Day 11 — Git and GitHub

### Current Curriculum

- **Phase:** 2 — Programming Foundations. **Sub:** `git`.
- **Objectives:** explain what version control solves; use the core Git cycle (change, stage,
  commit, push); describe branches and pull requests and why teams use them.
- **Lesson structure:** Concept intro (10m, Git as snapshots-over-time, Git vs. GitHub) → Core
  material (20m, working directory/staging/commit/push cycle, commit messages as documentation,
  branches and pull requests as the review checkpoint) → Hands-on (15m, init a repo, commit Day
  9/10 scripts, branch/edit/merge) → Practice (10m, `.gitignore` a secrets file and verify with
  `git status`) → Reflection (5m, why committing an API key is dangerous even if deleted next
  commit).
- **Example:** "History is permanent" — a leaked API key committed then deleted is still in
  history and gets harvested by scanners; the fix is revoke-and-rotate, not delete.
- **Resources (2, both `verified: true`):** Pro Git (the official free book), GitHub's "Get
  started" docs.
- **Quiz (5 questions):** what a commit is; whether deleting a secret later removes it from
  history (correctly `false`); why branch; the organizational value of a pull request; why commit
  messages matter.

### Pedagogical Audit

1. **Accuracy** — correct throughout. The "history is permanent, revoke don't delete" framing is
   the accepted correct practice, not a simplification that misleads.
2. **Clarity** — strong.
3. **Depth** — appropriate; deliberately does not cover rebase, merge-conflict resolution, or
   `.git` internals — correct for a first Git exposure.
4. **Practicality** — high; the hands-on task uses the learner's own Day 9/10 scripts, not a
   throwaway demo repo, and the practice task (`.gitignore` a secrets file) is a genuinely useful
   habit tied directly to the day's own secrets-in-history warning.
5. **Examples** — the leaked-API-key example is concrete, accurately describes real-world scanner
   behavior (credentials pushed publicly are harvested within minutes — a widely documented and
   still-current risk, not something in need of updating), and correctly prescribes revoke/rotate
   over delete.
6. **Active learning** — yes: real repo, real commits, real branch/merge, real `.gitignore` check.
7. **Misconceptions** — "commit ≠ push" and "commit is not a backup strategy" both addressed
   directly and correctly in `salahPaham`.
8. **Current relevance** — no material gap. GitHub's shift away from password-based `git push`
   authentication (toward tokens/SSH) is a real change from recent years, but the lesson never
   claims or implies password authentication — it stays at the conceptual/workflow level (stage,
   commit, push, branch, PR) and does not specify an authentication mechanism, so this is not a
   gap in what the lesson actually teaches, only a topic it correctly leaves out at this depth.
9. **Resource quality** — both official (Git's own book, GitHub's own docs); appropriately
   leveled for a first exposure.
10. **Assessment alignment** — all three objectives tested: q1 tests what version control
    solves via "what is a commit"; q3/q4 test branches and PRs directly; q2/q5 test the
    history-permanence and message-documentation points from Core material and the Example.
    Strong.

## Day 12 — What AI Actually Is

### Current Curriculum

- **Phase:** 3 — AI Foundations. **Sub:** `ai-fundamentals`.
- **Objectives:** place AI/ML/DL in the correct nested relationship; explain the shift from
  rule-writing to pattern-learning; decide whether a given problem is a reasonable AI candidate.
- **Lesson structure:** Concept intro (10m, AI as the broad field, ML and DL as nested subsets) →
  Core material (20m, rule-based vs. learned systems, where the inversion helps vs. is unnecessary,
  the "no guarantee of correctness" honesty frame) → Hands-on (15m, classify three real work tasks
  as rules-based/learnable/hybrid) → Practice (10m, for one learnable task, specify data needed,
  cost of a wrong answer, and detection method) → Reflection (5m, complete "AI is the wrong tool
  for this task when...").
- **Example:** an LLM asked to calculate final grades — usually right, occasionally silently
  wrong; grading is a known deterministic rule that belongs in code, not a model.
- **Resources (3, all `verified: true`):** Google's Machine Learning Crash Course (framing
  section), Microsoft's open "ML for Beginners" curriculum, DeepLearning.AI's "AI for Everyone"
  (Coursera, explicitly scoped to Week 1 with cost/duration disclosed).
- **Quiz (6 questions):** AI⊃ML⊃DL nesting; what changes moving from rules to learning; poorest
  LLM-suitability candidate (grade calculation, correctly flagged); generalization-limit
  true/false; the best suitability-screening question; short-answer on why AI output shouldn't be
  treated as truth by default.

### Pedagogical Audit

1. **Accuracy** — correct throughout. The nested-circle AI⊃ML⊃DL framing is the standard,
   still-current framing used across major AI education sources (matches, for instance, the
   framing this project's own Day 12 resource — Google's Machine Learning Crash Course — uses,
   per its own `apa`/`inti` summary already in the resource entry).
2. **Clarity** — strong; the "nested circles, not synonyms" phrasing directly heads off the most
   common beginner confusion.
3. **Depth** — appropriate. Deliberately does not reach into generative AI or LLM specifics —
   those are correctly deferred to Days 15–17, which this day is a prerequisite for, not a
   duplicate of.
4. **Practicality** — high; the "AI suitability screen" activity (rule known? data available?
   cost of wrong answer?) is a genuinely transferable organizational decision framework, not a
   toy exercise.
5. **Examples** — the grade-calculation example is sharp and specific: it names exactly why
   fluent-but-wrong output is dangerous (no error, just a wrong number stated confidently) and
   correctly separates "compute the grade" (code) from "explain the grade" (model).
6. **Active learning** — yes: classify real tasks from the learner's own work, rank them, defend
   the weakest candidate.
7. **Misconceptions** — "no guarantee of correctness" and the payroll-deduction absurdity example
   directly address the common misconception that ML is a universal upgrade over rules.
8. **Current relevance** — no gap found. The lesson's own resource commentary already discloses
   the audit/certificate cost structure and module count for the Coursera resource (evidence this
   day's resource notes are actively maintained, not stale defaults).
9. **Resource quality** — all three official/high-credibility, and deliberately differentiated
   (Google = technical framing, Microsoft = hands-on practice, Coursera = organizational judgment)
   rather than three overlapping restatements of the same content.
10. **Assessment alignment** — all three objectives tested directly: q1 tests the nested
    relationship; q2/q4 test the rules→learning shift and its correctness implications; q3/q5
    test suitability judgment (including the exact grading-example scenario from Core material);
    q6 tests the "don't treat output as truth" point from the honesty frame. Strong, direct
    coverage across all objectives.
