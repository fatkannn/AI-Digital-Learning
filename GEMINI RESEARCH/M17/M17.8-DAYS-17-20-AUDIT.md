## Day 17 — Prompting, System Instructions and Structured Output

### Current Curriculum

- **Sub:** `prompting`. **Objectives:** write prompts with explicit goal/context/constraints/
  output format; explain system instructions vs. user messages; request structured output and
  validate it before use.
- **Lesson structure:** Concept intro (prompt-as-specification framing) → Core material (the
  five prompt elements; system vs. user message durability, tied back to Day 16's own
  forgotten-formatting-rule example; structured output as a request, not a guarantee;
  zero-shot vs. few-shot; XML-style delimiters as the prompt-injection boundary, forward-
  referencing AI security) → Hands-on (write a JSON-quiz-generation prompt, run 3x, check
  shape consistency) → Practice (add explicit constraints, observe effect) → Reflection
  (fallback behavior for non-JSON output).
- **Resources (2, both `verified: true`):** Anthropic's "Prompting best practices" (already
  re-verified and URL-corrected in M15 Batch 4, §42) and Google's Gemini API structured-output
  docs.
- **Quiz (8 questions):** goal/context/constraints/format; system-instruction durability;
  JSON-not-guaranteed; defensive-parsing fallback; explicit-criteria-over-adjectives (twice,
  from two angles); delimiter/injection boundary; short-answer on ambiguous instructions.

### Pedagogical Audit

1. **Accuracy** — correct throughout; the system-vs-user-message distinction and the
   defensive-parsing stance on structured output both match current best practice.
2. **Clarity** — strong; "prompt is a specification, not a magic phrase" is a clean framing
   carried through the whole day.
3. **Depth** — appropriate; goes far enough to name zero-shot/few-shot and delimiters without
   drifting into prompt-engineering minutiae.
4. **Practicality** — high; the hands-on task (generate JSON quiz items, run 3x, check
   consistency) directly exercises the day's central claim that specification beats phrasing.
5. **Examples** — the "constraints beat phrasing" example is concrete and mirrors the
   day's own hands-on task.
6. **Active learning** — yes, twice: an initial prompt-and-compare, then a
   constrain-and-rerun iteration.
7. **Misconceptions** — explicit: "requesting JSON is not a guarantee of receiving it."
8. **Current relevance** — **no material gap found.** The advice given (parse defensively,
   validate against schema, define failure behavior) is durable, vendor-agnostic guidance that
   remains correct regardless of any single vendor's structured-output guarantees improving —
   teaching "trust but verify" here is arguably more valuable for a beginner than teaching one
   vendor's specific API surface, which the curriculum deliberately treats as out of scope for
   this conceptual day (vendor APIs are Days 7 and 22's territory). Considered and rejected as
   a candidate enhancement, not silently skipped.
9. **Resource quality** — both resources credible, complementary (Anthropic's general
   prompting reference; Google's JSON-specific docs), no redundancy.
10. **Assessment alignment** — all three objectives directly assessed (q1: elements; q2:
    system instructions; q3/q4: structured-output validation), plus the taught-but-not-formally-
    objective content (few-shot/delimiters) is also assessed (q5/q6/q7). No gap.

### Research Findings

how fast that specific API surface moves — was resolved by direct inspection: the lesson
teaches the durable principle (validate, don't trust), not a vendor-specific mechanism, so
there is nothing time-sensitive to update.

## Day 18 — Embeddings and Vector Search

### Current Curriculum

- **Sub:** `embeddings`. **Objectives:** explain what an embedding represents and why
  similarity is distance; describe chunking and why it determines retrieval quality;
  distinguish semantic from keyword search by failure mode.
- **Lesson structure:** Concept intro (embedding as numeric meaning) → Core material (cosine
  distance; semantic-vs-keyword trade-off in both directions — semantic finds paraphrases,
  keyword wins on exact identifiers; chunking as "the quiet determinant of quality," with
  structure-aware splitting recommended over fixed-character splitting) → Hands-on (chunk one
  document two ways, compare) → Practice (five realistic questions, mark which strategy
  retrieves correctly) → Reflection (why a topically-relevant chunk can still be useless).
- **Resources (2, both `verified: true`):** Pinecone's vector-database explainer (re-verified
  claim-by-claim in M15 Batch 1, §39) and Hugging Face's `/learn` root (embeddings/semantic
  search).
- **Quiz (6 questions):** embedding definition; keyword-search strength (exact identifiers);
  chunk-size effect on retrieval; chunk-boundary failure diagnosis; semantic-match mechanism;
  short-answer on chunk metadata.

### Pedagogical Audit

1. **Accuracy** — correct; cosine distance, the semantic/keyword trade-off in both
   directions, and the chunking guidance all hold up.
2. **Clarity** — strong; "find related content becomes find nearby vectors" is an effective
   one-line reframe.
3. **Depth** — appropriate; deliberately stops short of ANN indexing algorithms (HNSW etc.),
   which the linked Pinecone resource covers for the learner who wants more.
4. **Practicality** — high; the two-ways-of-chunking hands-on task is directly tied to the
   day's central claim.
5. **Examples** — the "chunk that lost its heading" example (parental-leave entitlement split
   from its jurisdiction heading) is concrete and precisely illustrates the chunking failure
   mode the day teaches.
6. **Active learning** — yes: chunk-and-compare, then five-question retrieval mapping.
7. **Misconceptions** — explicit: semantic search is not "smarter," it trades one failure mode
   for another (bad on exact identifiers).
8. **Current relevance** — **no material gap found.** The core mechanics (embeddings, cosine
   distance, chunking trade-offs) are stable, foundational concepts that have not shifted.
9. **Resource quality** — both appropriately leveled and relevant. **Minor observation, not a
   finding:** the Hugging Face resource is the same generic `/learn` root URL also used on Day
   19 (see below) — a pattern already present before M17 and not something this session was
   asked to correct (resource replacement requires strong evidence per the M17 resource rule,
   and a shared root URL across two related days is not evidence of unsuitability, only of
   imprecision already accepted in earlier verification passes).
10. **Assessment alignment** — all three objectives directly assessed (q1: embedding
    definition; q3/q4/sa: chunking; q2/q5: semantic-vs-keyword). No gap.

### Research Findings

None opened. Nothing in the lesson's factual claims is time-sensitive enough to warrant an
external check — embeddings-as-vectors and cosine similarity are not concepts that go stale.

## Day 19 — RAG: Retrieval-Augmented Generation

### Current Curriculum

- **Sub:** `rag`. **Objectives:** describe the full RAG pipeline and where each stage can
  fail; explain what RAG does and does not fix; design a RAG evaluation that measures
  retrieval and generation separately.
- **Lesson structure:** Concept intro (retrieval instead of relying on trained knowledge) →
  Core material (full pipeline: chunk → embed → store → retrieve → optionally rerank →
  generate with citation instruction; per-stage failure enumeration; RAG constrains but does
  not eliminate hallucination; RAG-vs-fine-tuning distinction — weights untouched, context
  window is what changes, decisive for frequently-changing content) → Hands-on (build a
  retrieval ground truth for ten questions) → Practice (define retrieval-hit-rate and
  answer-faithfulness as two separate metrics) → Reflection (why the first diagnostic
  question is not the prompt).
- **Resources (2, both `verified: true`):** Hugging Face `/learn` root (RAG concepts) and
  Google's Gemini API grounding docs.
- **Quiz (7 questions, including one scenario question on RAG vs. fine-tuning for
  frequently-changing policy content):** pipeline order; hallucination-not-eliminated;
  retrieval-first diagnosis; why two separate metrics; contradictory-source behavior;
  RAG-vs-fine-tuning scenario; short-answer on why retrieved context beats trained knowledge
  for internal policy questions.

### Pedagogical Audit

1. **Accuracy** — correct and precise, including the frequently-cited-but-often-blurred
   RAG-vs-fine-tuning distinction (weights untouched; only the context window changes).
2. **Clarity** — strong; the "split the diagnosis" framing (retrieval failure vs. generation
   failure, two different owners) is an effective mental model.
3. **Depth** — appropriate; covers the full pipeline plus both major misconceptions
   (hallucination-eliminated, fine-tuning-is-equivalent) without overreaching into
   reranking-algorithm specifics.
4. **Practicality** — high; building a retrieval ground truth and defining two separate
   metrics are both directly transferable to real RAG evaluation work.
5. **Examples** — the "splitting the diagnosis" example (7 of 10 failures were retrieval
   failures, not generation failures) makes the two-metrics argument concrete with a
   specific, plausible number.
6. **Active learning** — yes: ground-truth construction, then metric definition.
7. **Misconceptions** — explicitly addressed, twice (hallucination is constrained not
   eliminated; RAG and fine-tuning are not interchangeable).
8. **Current relevance** — **no material gap found.** The RAG pipeline description and the
   RAG-vs-fine-tuning distinction remain the standard framing; nothing here has dated.
9. **Resource quality** — both appropriate. Same shared-root-URL observation as Day 18 (the
   Hugging Face `/learn` root is reused); noted, not escalated — this is a pre-existing,
   already-`verified: true` pattern, not new to this audit.
10. **Assessment alignment** — all three objectives directly assessed (q1: pipeline order;
    q2/q5/q6: what RAG does/doesn't fix; q4: separate-metrics rationale). No gap.

### Research Findings

None opened. The RAG-vs-fine-tuning distinction and pipeline description are stable,
well-established concepts; no time-sensitive claim required external verification.

## Day 20 — Tool Calling and AI Agents

### Current Curriculum

- **Sub:** `agents`. **Objectives:** explain tool calling as a request-execute-return loop;
  distinguish a workflow from an agent by who decides the next step; identify where autonomy
  adds risk and what controls belong around it.
- **Lesson structure:** Concept intro (a model cannot act — it emits a structured request)
  → Core material (tools defined by name/description/parameter schema, vague descriptions
  degrade reliability more than vague prompts; workflow-vs-agent distinction by who decides
  sequencing; five concrete controls — least privilege, human approval before consequential
  actions, iteration/cost limits, full logging, treating agent-read content as data not
  instructions — with prompt injection named as "the defining security problem of agent
  systems") → Hands-on (design three tools for an e-learning assistant, mark which needs human
  confirmation) → Practice (write a tool-misuse failure story) → Reflection (when a fixed
  workflow beats an agent).
- **Resources (2, both `verified: true`):** Anthropic's Tool use overview (URL already
  migrated to platform.claude.com and re-verified, §10/M10 and §42/M15) and the official Model
  Context Protocol site.
- **Quiz (6 questions):** who executes a tool call; workflow-vs-agent distinction; prompt
  injection (content-as-data); human-confirmation control; why vague tool descriptions hurt
  reliability; short-answer on workflow-over-agent reasoning.

### Pedagogical Audit

1. **Accuracy** — correct throughout; the workflow-vs-agent distinction (who decides
   sequencing) matches how this distinction is drawn in current authoritative treatments of
   the topic, and the five listed controls are standard current practice.
2. **Clarity** — strong; "a model cannot act, it can only emit a request" is an effective,
   memorable framing that the rest of the day builds on.
3. **Depth** — appropriate; goes deep enough into agent safety (five concrete controls, named
   prompt-injection risk) without drifting into a specific orchestration framework's API.
4. **Practicality** — high; designing three named tools and marking which needs human
   confirmation is a direct, transferable design exercise.
5. **Examples** — the "document that gave orders" example (a document instructing the agent to
   exfiltrate content via email) is a clean, concrete illustration of prompt injection via
   agent-read content, and ties directly to the "content is data, not instructions" control.
6. **Active learning** — yes: tool design with a human-confirmation judgment call, then a
   failure-story exercise.
7. **Misconceptions** — explicit: "agent is not a better version of workflow" — it trades
   predictability for flexibility, and the choice should default to the least autonomy the
   problem requires.
8. **Current relevance** — **no material gap found upon inspection**, with one angle
   deliberately considered and rejected: this is one of the fastest-moving topics in the
   curriculum (agentic AI, tool-use APIs, MCP), so a currency check was warranted before
   settling on KEEP. The five listed controls (least privilege, human approval, iteration/cost
   limits, logging, treat-content-as-data) are architecture-level, vendor-agnostic principles
   that remain the current standard framing for agent safety — nothing here names a specific
   product feature or metric that could go stale independent of the underlying principle. No
   external source was opened because the content did not turn on any single, checkable,
   time-sensitive fact — unlike Day 16's "context rot," which was a specific named phenomenon
   worth sourcing, nothing on Day 20 presented an equivalent single verifiable claim.
9. **Resource quality** — both resources are official, primary, and already correctly
   maintained (Anthropic URL migration already handled in an earlier session; MCP site is the
   protocol's own official home). No gap.
10. **Assessment alignment** — all three objectives directly assessed (q1/q5: tool-calling
    loop and description quality; q2/sa: workflow-vs-agent; q3/q4: autonomy risk and
    controls). No gap.

### Research Findings

None opened, for the reason stated in Pedagogical Audit point 8: no single, time-sensitive,
independently-checkable factual claim was present to verify — the day teaches durable
architectural principles, not a specific product surface.
